メッシュの**スムース法線**を計算してメッシュへベイクし、背面押し出しアウトラインのハードエッジでの割れを解消します。

ツール本体は純粋なエディター C# で、**レンダーパイプラインに依存しません**。アウトラインシェーダーはパイプライン別に Sample として提供され（URP / Built-in）、必要な方だけをインポートします。

---

## 1.6.x 以前からのアップグレード

**頂点カラーまたは接線チャンネルだけで保存しているプロジェクトは影響を受けません**。この節は読み飛ばしてかまいません —— その 2 つのフォーマットは 1 バイトも変わっていません。

`1.7.0` では **UV チャンネル**の保存フォーマットを「3 成分の生の方向」から「2 成分の八面体エンコード」へ変更しました。新しいシェーダーは古いデータをデコードできず、**しかもこれは GPU 側では検出できません** —— 頂点アセンブリが欠けた成分を 0 で埋めるため、2 成分のデータと「z がちょうど 0」の 3 成分データはシェーダー内でビット単位に同一になり、どんな判定基準にも本物の反例が存在します。したがって自動互換の余地はなく、ベイクし直すしかありません。

症状は**アウトラインの向きが全体的に崩れる**ことで、エラーは一切出ません。

### 組み込み方別に確認する

| 自分の使い方 | パッケージ更新後 | やるべきこと |
| --- | --- | --- |
| **Pass テンプレートを使用**、または `OSN_GetSmoothNormalOS` / `OSN_DecodeTexCoord` を呼び出し | デコード処理がパッケージと一緒に更新され、**古いデータを新フォーマットとして読み始めます** | 一度ベイクし直す |
| **「最小の書き方」に従って** `normalize(v.uv1.xyz)` を手書き | **影響なし**。本ライブラリのデコーダーを呼んでいないため | ⚠ 下記の個別説明を参照 |
| `CustomStorageWriter` デリゲートで独自に保存 | 影響なし。エンコード / デコードはすべて自分の手の内 | なし |

> ⚠️ **`normalize(v.uv1.xyz)` を手書きしているプロジェクトが最も落とし穴にはまりやすい**です：パッケージを更新した時点では何も起こらないため、自分は影響を受けないと思い込みがちですが、**一度ベイクし直した途端に壊れます**。ベイクし直す前に、その 1 行を `OSN_OctDecode(v.uv1.xy)` へ変更してください。この 2 つは必ずセットで行う必要があります。

### 自動で移行されるメッシュ

`AssetPostprocessor` のバージョン番号を上げたため、**[インポート時の自動ベイク](#インポート時の自動ベイク)を有効にしていて、かつモデルインポーターから生成されたメッシュ**は、アップグレード後に自動で再インポートされ、再ベイクされます。

**以下の 2 種類は自動では行われません**。手動で一度ベイクし直してください：

- ツールウィンドウで**手動ベイク**したメッシュ
- **独立した `.asset` として保存**した Mesh（インポート成果物ではないため）

### どのメッシュが旧フォーマットのままか確認する

ツールウィンドウでメッシュを選び、右カラムの「データチャンネル状態の一覧」を見てください：成分数が 3 の TEXCOORD チャンネルには **`▲ 旧フォーマットの可能性`** が付きます。そのチャンネルで一度生成し直せば移行完了で、マテリアルは触る必要がありません。

これは**強いヒントであって判定ではありません** —— メッシュ結合は UV の次元を最大値に揃えますし、3 成分の方向を UV へ書き込む他のツール（植生の風、VAT など）も同じように一致します。逆に、移行後の 2 成分データは通常のテクスチャ UV と数値上まったく区別がつかないため、「データあり」としか表示されません。

## アウトラインシェーダーのインポート（必須）

> このドキュメントは**すでに本パッケージをインストール済み**のユーザー向けです。インストール方法（UPM git URL / `Packages/` へコピー）はリポジトリルートの README を参照してください。

コアパッケージにアウトラインシェーダーは**含まれません** —— それだと特定のパイプラインに依存してしまうためです。Package Manager で本パッケージを選択 → `Samples` → **自分のプロジェクトのパイプラインに合う方をインポート**してください：

| Sample | シェーダー名 |
|---|---|
| Outline Shader (URP) & Demo | `OutlineSmoothNormalsGenerator/Outline URP` |
| Outline Shader (Built-in RP) & Demo | `OutlineSmoothNormalsGenerator/Outline Built-in` |

名前が異なるため共存できますが、プロジェクトのパイプラインは 1 つなので通常は該当する方だけで十分です。

> ツール本体はコアパッケージ内にあり、メニュー **`Tools > Smooth Normal Generator`** はインストール後すぐに使えます。Sample のインポートはアウトラインシェーダーを取得するためのもので、ツールメニューの表示とは関係ありません。

## クイックスタート

![「スムース法線生成」タブ：左が操作パネル、右上がデータチャンネル状態、右下がリアルタイムアウトラインプレビュー](./Docs~/Images/tool_generate.png)

### 1. ツールを開く

`Tools > Smooth Normal Generator`

### 2. 対象を選ぶ

対象を選択するとツールが自動で読み込みます。対象は次のいずれかです：

- **シーン内のオブジェクト / モデル**（`.fbx` / `.obj` など）**/ プレハブ** —— いずれも**階層全体をたどって**（子オブジェクト含む）その中のすべてのメッシュを収集します。
- **Mesh アセット** —— Project 内の独立した `.asset`、または FBX を展開して選んだ Mesh サブアセットは、そのまま対象になります。

上記のいずれかを「対象」欄に手動でドラッグしてもかまいません。

複数のメッシュがある場合、対象欄に**チェックボックスのスクロール一覧**が表示されます（上部に「すべて選択 / クリア」、新しいソースを読み込むと既定で全選択、同じメッシュが複数のレンダラーで共有される場合は自動で重複排除）。**チェック**が「生成 / 保存 / 別名で保存」の対象と、プレビューに表示するメッシュを決めます。**メッシュ名をクリック**するとそれが**フォーカス**になり、右側のメッシュ情報とチャンネル状態はフォーカスのメッシュを表示します。

### 3. メッシュが書き込み可能か確認

メッシュが `.fbx` などのモデルファイル由来の場合、それは**読み取り専用のインポート済みサブアセット**です —— 書き込んだデータは次回の再インポート時に失われます。ツールはこれを検出して保存を阻止するので、**`⧉ 独立した Mesh として保存…`** で書き込み可能な `.asset` を複製してください。

> **シーン内のオブジェクト**を選択している場合、新しい `.asset` は自動的にオブジェクトへ再割り当てされます。**アセット**（Mesh / モデル / プレハブ）を選択している場合は書き戻す先のコンポーネントがないため、独立した `.asset` が作られるだけです —— ご自身で参照してください。独立した書き込み可能な `.asset` メッシュはそのまま書き込めるので、複製せずステップ 4 で保存すれば済みます。

### 4. 保存方式を選んで生成

[保存方式](#保存方式)（どのチャンネルへ書くか）と[保存空間](#保存空間)（どの空間で書くか。**既定は接線空間**で、スキンメッシュには必須）を選んでから **`▶ スムース法線を生成`** をクリックし、**`保存`** でディスクへ書き出します。

> この 2 つは後でマテリアル側でも**同じものを選ぶ**必要があります。違っているとアウトラインが正しくならず、しかもエラーは出ません。

### 5. プレビュー

ウィンドウ右側がリアルタイムプレビューです（**埋め込み型**で、別ウィンドウではありません）。**チェック**したすべてのメッシュを表示します（複数選択時は階層内の相対位置に配置し、カメラが全体を収めます。何もチェックしていないときはプレースホルダーを表示）：

- 左ドラッグで回転、ホイールでズーム、中ドラッグでパン
- **スムース法線を表示**（緑）と**元の法線を表示**（青）を重ねて比較（フォーカスのメッシュ）
- アウトラインの幅・色、モデルのスムースネス / メタリック、背景色を調整

プレビューは実際の描画とまったく同じデコード / 押し出し処理を共有しているため、見たままの結果が得られます。

## UI 詳細

ツールウィンドウ上部には 2 つのタブがあります：**スムース法線生成**（手動フロー）と **インポート自動ベイク**（[インポート時の自動ベイク](#インポート時の自動ベイク)を参照）。本節は「スムース法線生成」タブの各機能ブロックを上から順に説明します —— レイアウトは上記[クイックスタート](#クイックスタート)のスクリーンショットと合わせて確認してください：**左カラムが操作パネル、右カラムは上半分がデータチャンネル状態、下半分がリアルタイムプレビューとパラメーターです。**

### UI の言語

各タブのヘッダーの下に **`中文` / `English` / `日本語`** の切り替えボタンがあります。押した瞬間に
切り替わり、左右のカラム、ヘルプボックス、ダイアログ、Console のログ、アウトラインマテリアルの
Inspector まで一斉に追従します。**既定は中国語です。**

- 設定は **`EditorPrefs`**（キー `OutlineSmoothNormals.Language`）に**マシンごと**保存されます。
  バージョン管理には入らないため、言語を切り替えてもチームメンバーの差分にはなりません。
  別の Unity プロジェクトで本パッケージを開いても選択は保持されます。
- 2 つのタブがそれぞれボタンを描画しますが、設定値は同じです —— どちらで切り替えても同じです。
- 正確さのため、**英語用語は 3 言語とも原文のまま**残します：`TEXCOORD1 (mesh.uv2)`、
  `SkinnedMeshRenderer`、`tangent.xyz`、`Read/Write` などの識別子は翻訳せず、中国語と日本語の
  保存方式ボタンには英語名を併記します（例：`頂点カラー / Vertex Color`）。
- マテリアルパネルの **`Smooth Normal Source` / `Vertex Color Channel` / `Smooth Normal Space`
  の 3 つは、3 言語とも英語名で表示されます** —— 本ドキュメントはまさにその名前で案内しているため、
  翻訳すると逆に見つけられなくなります。

> メニューパス `Tools > Smooth Normal Generator` はローカライズできません（Unity の `MenuItem` は
> 定数文字列を要求するため）。3 言語とも英語のままです。

### 左カラム · 対象
- **対象**：現在のソースオブジェクト / アセット。右の `×` でクリアできます。シーンオブジェクト、Mesh、モデル、プレハブをこの欄へ直接ドラッグできます。
- **メッシュ一覧（N / M 選択中）**：ソースから見つかったすべてのメッシュ。上部の `すべて選択` / `クリア` でチェックを一括切り替えします。
  - **チェックボックス**がバッチ処理の対象を決めます —— 「生成 / 保存 / 別名で保存」は**チェックしたすべてのメッシュ**に作用し、プレビューにも全部が同時に表示されます。
  - **メッシュ名をクリック**するとそれが**フォーカス**（ハイライト行）になります：「メッシュ情報」「データチャンネル状態」、およびプレビューの「法線可視化オーバーレイ」はフォーカスのメッシュのみを対象とします。
  - 各行にはレンダラー種別（`MeshFilter` / `SkinnedMeshRenderer`）が付きます。フォーカスのメッシュの下には、レンダラーとメッシュ名を示す 2 つのタグがあります。
  - 下部の情報バーには、現在のチェック数と「バッチは全体に作用、状態はフォーカスのみ表示」というルールが示されます。

### 左カラム · メッシュ情報（折りたたみ）
展開すると、フォーカスのメッシュの**頂点数・三角形数・サブメッシュ数**、および**法線 / 接線 / 頂点カラー**の有無、各 **TEXCOORD0–7** チャンネルにデータがあるか（成分数付き）を一覧できます。書き込み前に対象チャンネルが既に使用済みかを素早く確認できます。

### 左カラム · 保存方式
3 つのタブ **頂点カラー / 接線チャンネル / UV チャンネル** で、スムース法線をどこへ書くかを決めます（トレードオフは[保存方式](#保存方式)を参照。ボタンにマウスを乗せても説明が出ます）：
- **頂点カラー**：`RG / GB / BA` のペアを選択。下の「頂点カラーチャンネル状態」が、各チャンネルで**上書きされる**成分を示します（例：BA モードでは B←法線 X、A←法線 Y）。選択していないチャンネルは元の値を保ちます。`RG / GB / BA をクリア` でペア単位に消去します。
- **接線チャンネル**：方向を `tangent.xyz` へ直接書き込みます。⚠ 元の接線を上書きするため、戻したいときはパネルの「接線を再計算」で本物の接線を求め直してください。
- **UV チャンネル**：ドロップダウンで `TEXCOORD0–7` を選択（チャンネル単位でクリア可）。`TEXCOORD0`（メインテクスチャ UV）を選ぶと確認を求められます。

### 左カラム · 保存空間
保存方式パネルのすぐ下にある 2 つのタブ **オブジェクト空間 / 接線空間** で、方向そのものをどの空間で書くかを決めます —— 「どのチャンネルへ書くか」とは**直交**した別の話です（原理は[保存空間](#保存空間)を参照。ボタンにマウスを乗せると詳しい説明が出ます）。

- **既定は接線空間**です。静的モデルにもスキンメッシュにも正しいためです。
- **接線チャンネル**保存を選んでいるときはブロック全体がグレーアウトします：そのときは接線自体がデータであり、再構築するための基底がなく、その必要もありません。
- ⚠ マテリアル側の「保存空間」もここと**同じものを選ぶ**必要があります。違っているとアウトライン全体が傾き、エラーは一切出ません。

### 左カラム · 生成
- **結合トレランス**スライダー（既定 `0.0001`、[結合トレランス](#結合トレランス)を参照）。
- **▶ スムース法線を生成** ボタン：現在の保存チャンネルとチェック数をラベルにリアルタイム表示（例「→ 頂点カラー ×6」）。クリックするとチェックしたすべてのメッシュに対して計算し、`sharedMesh` へ書き込みます。
- フォーカスのメッシュにデータの問題があると、このブロックの上部に**健全性チェック**カードが表示されます（[メッシュ健全性チェック](#メッシュ健全性チェック)を参照）。エラーがある場合は生成前に確認を求められます。

### 左カラム下部 · 保存
下部に固定された `↺ 今回の変更を元に戻す`、`保存`、`⧉ 独立した Mesh として保存…` の 3 ボタン。作用と注意点は[データ安全性](#データ安全性)を参照してください。

### 右カラム上 · データチャンネル状態の一覧
頂点カラー / 接線 / TEXCOORD の 3 枚のカードが、各チャンネルの状態（「データあり / 空」など。判定基準と表記は[データ状態](#データ状態)参照）を示します。常に**フォーカス**のメッシュを反映します。

### 右カラム下 · アウトラインプレビューとパラメーター
埋め込み型のリアルタイムプレビュー：**左ドラッグで回転、ホイールでズーム、中ドラッグでパン**。左上のバッジ（例「● 頂点カラー · 接線空間」）は、プレビューが現在どのチャンネル・どの空間でデコードしているかを示す**読み取り専用**の表示で、左側の「保存方式」と「保存空間」に追従します。プレビューは製品用シェーダーと 1 つのデコード / 押し出し処理を共有しており、見たままの結果が得られます。右側のパラメーターパネルは上から順に：

| グループ | パラメーター | 説明 |
|---|---|---|
| **アウトライン** | アウトラインを表示 | アウトライン Pass のオン / オフ。 |
| | アウトライン色 | アウトラインの色。 |
| | アウトライン幅 | `0.001–0.1`。シェーダーの `_OutlineWidth` と同スケールで直接対照可能。 |
| | 幅モード | **スクリーンスペース**（等幅・距離に依存しない）/ **ワールドスペース**（ワールド単位でオフセット・距離とともに縮小）。 |
| **モデル** | モデルを表示 | 基本モデルのオン / オフ（アウトラインだけ見たいときはオフに）。 |
| | ベースカラー / スムースネス / メタリック | プレビューマテリアルの見た目。スムースネス・メタリックは範囲 `0–1`。 |
| **ビューポート** | 背景色 | プレビューの背景色。 |
| **法線可視化** | スムース法線を表示 | 緑のスムース法線の線分を重ねて表示。 |
| | 法線の長さ | 線分の長さ、`0.005–0.5`。 |
| | スムース法線の色 | スムース法線の線分の色。 |
| | 元の法線を表示 | 青の元の法線を重ね、ハードエッジでの向きの差を比較。 |
| | 元の法線の色 | 元の法線の線分の色。 |
| | **Scene ビューに表示** | 上記 2 種類の法線を Scene ビューにも同時に描画します。詳細は次節を参照。 |
| **カメラ** | 水平回転 / 垂直回転 / 距離 | 視点を正確に設定（ビューポート上でドラッグ / ホイールしても可）。 |
| | 視点をリセット | 角度を初期化し、チェックしたすべてのメッシュを自動的に収めます。 |

> 埋め込みプレビュー内のオーバーレイ線分は**フォーカス**のメッシュのみに描かれます。一方、プレビューの描画は**チェックしたすべての**メッシュを表示します（複数選択時は階層内の相対位置に配置）。

### Scene ビューでの法線オーバーレイ

埋め込みプレビューが描いているのは**バインドポーズ**の静的なメッシュなので、スキニングによる差は見えません —— しかし[接線空間での保存](#保存空間)の意義は、まさに「スキンアニメーション下でアウトラインが裂けない」ことにあります。「**Scene ビューに表示**」にチェックを入れれば、実際のシーンでそれを検証できます：

- **チェックしたすべてのシーン内メッシュ**に作用します（直接選択した Mesh アセットはシーン上の位置を持たないため、スキップされてその旨が表示されます）。
- `SkinnedMeshRenderer` は**現在のポーズ**を取ります —— **アニメーション再生中**も法線は常に表面に沿っているはずです。関節部分で扇のように広がるなら、データをベイクした空間とマテリアルで選んだ空間が食い違っています。
- 頂点数が多すぎる場合は自動的に間引かれ、パネルに「1/N でサンプリングして表示中」と**正直に表示**されます。
- Scene の再描画のたびに計算し直すため、調査時のみオンにすることを推奨します。ツールウィンドウを閉じれば描画は自動的に停止します。

## 保存方式

スムース法線はメッシュのどこかの頂点データへ書き込む必要があります。3 つの方式はいずれも**完全な三次元方向**を格納し、違いは「どのデータを占有するか、精度はどれだけか、何と衝突するか」だけです —— 方式の選択は実質「このメッシュのどのデータが空いているか」に答えることになります。

| 保存方式 | 精度 | 占有 | 主な衝突 |
| --- | --- | --- | --- |
| **頂点カラー** | 約 1°（八面体エンコード、8-bit × 2） | 最小。バイトチャンネル 2 つ | 選んだチャンネルペアを上書き。モデルの頂点カラーを別用途（AO / マスク / 風）に使っていると衝突 |
| **接線チャンネル** | 完全な float 3 つ | `tangent` 丸ごと | ⚠ 元の接線を上書き → **ノーマルマップが機能しなくなる** |
| **UV チャンネル** | 約 5e-6°（八面体エンコード、float × 2） | UV チャンネル 1 つ（頂点あたり float 2 つ） | 最小。⚠ ただし `TEXCOORD0` はメインテクスチャ UV で、書き込むとテクスチャマッピングが壊れます |

頂点カラーの 1° の誤差はアウトライン押し出しで知覚できる水準をはるかに下回るので、**既定のままで十分**です。ノーマルマップが必要なら接線チャンネルは避け、頂点カラーが既に使われているなら `TEXCOORD1` 以降の空きチャンネルに切り替えてください。

> 八面体エンコードは全球面の全単射で、半球圧縮を行わないため符号の曖昧さがありません —— ハードエッジの角にある、位置が重なって法線だけが異なる頂点群も、同じ 1 本の方向にデコードされます。初期の「XY を格納 ＋ Z を再構築 ＋ 法線で符号を決める」方式が、まさに直すべきだった角でアウトラインを割っていたのはこれが理由です。

> **UV チャンネルは `1.7.0` から 2 成分の八面体エンコードで保存します**（それ以前は 3 成分の生の方向）。2 つの `float32` による八面体の往復角度誤差は約 `5e-6°` で、`xyz` をそのまま格納した場合の `5e-7°` と同じく浮動小数点の丸め誤差の水準であり、その代わりに頂点あたり 4 バイトを節約できます。**`1.6.x` 以前でベイクした UV データは `1.7.0` ではデコードできません**。[1.6.x 以前からのアップグレード](#16x-以前からのアップグレード)を参照してください。

> ⚠️ 表の精度は**エディター内**での値です。Unity の `Project Settings → Player → Vertex Compression` は既定で、**ビルド時**に接線と lightmap UV 以外の TEXCOORD を `fp16` へ圧縮します。そのとき接線チャンネルと UV チャンネルの実際の誤差は約 `6e-3°` になります（それでも頂点カラーの 1° よりはるかに良く、方式の選択には影響しません）。頂点カラーはもともと 8-bit なので影響を受けません。

## 保存空間

「どのチャンネルへ書くか」と**直交**するもう 1 つの軸です：方向そのものをどの空間で格納するか。

| 保存空間 | 何を格納するか | 適用 |
| --- | --- | --- |
| **オブジェクト空間** | バインドポーズでのオブジェクト空間の方向。デコードすればそのまま使える | 静的モデルのみ |
| **接線空間** | 各頂点自身の TBN を基準とした座標。デコード時に**スキニング後**の法線と接線で再構築 | 静的モデルもスキンメッシュも正しい（**既定**） |

### なぜスキンメッシュに接線空間が必要か

`SkinnedMeshRenderer` のスキニングでは、Unity は **POSITION / NORMAL / TANGENT** を変換しますが、**COLOR と TEXCOORD はそのまま渡され、スキニングされません**。

そのため頂点カラー / TEXCOORD に入れたオブジェクト空間の方向は「頂点はボーンについていくのに、押し出し方向はバインドポーズのまま」となり、関節を曲げた途端にアウトラインが裂けます。

一方、接線空間の座標は**スキニング不変**です：`S = a·T + b·B + c·N` とすると、スキニングはその頂点におおよそ回転 `R` を与え、`N` と `T` も Unity によって一緒に変換されるので、`a·T' + b·B' + c·N' = R·S` —— まさにスキニング後にあるべき方向になり、`(a, b, c)` は不変のままです。ノーマルマップがボーンアニメーション上で正しく働くのとまったく同じ理屈です。

### 使用上のポイント

- **メッシュに正しい接線が必要**：モデルのインポート設定で `Tangents` を `None` にしないでください。ただし接線を**占有はしません** —— ここでの接線は「基底」であって格納場所ではないので、ノーマルマップはこれまで通り使えます。
- **接線チャンネル保存には適用されません**：基底の再構築に必要な接線そのものを上書きしてしまうためです。そもそも必要もありません —— Unity は `tangent.xyz` を方向として一緒にスキニングするので、格納したオブジェクト空間の方向は自然にアニメーションへ追従します。ツールでもこのモードを選ぶと「保存空間」は自動的にグレーアウトします。
- ⚠ **マテリアル側も同じものを選ぶ必要があります**。どちらの空間も格納しているのは単位方向 1 本だけで、データ自体からは見分けられません。間違えてもエラーは出ず、アウトライン全体が傾くだけです。
- ⚠ **モデルの再インポートでずれることがあります**：ベイクにはその時点の法線 / 接線データを使うため、後から異なる接線生成方式で再インポートすると、ベイク済みのデータは黙ってずれます。**そのため接線空間は[インポート時の自動ベイク](#インポート時の自動ベイク)との併用を推奨します** —— ベイクがインポートパイプライン内、接線生成の後に行われるので、常に同じソースから得られます。
- 精度は影響を受けません：エンコードするのは単位方向であり、空間が変わっても単位方向のままなので、頂点カラーは変わらず約 1° です。

> UV が退化している箇所（3 つの UV が共線または重複）では接線がゼロベクトルか法線と共線になり、直交基底を構成できません。この種の頂点は[メッシュ健全性チェック](#メッシュ健全性チェック)が割合で報告し、アウトラインはそこでは元の頂点法線に沿った押し出しに退化します。

## インポート時の自動ベイク

![「インポート自動ベイク」タブ：有効化スイッチ、判定ルール、保存方式、結合トレランス。設定は ProjectSettings/ に保存](./Docs~/Images/tool_auto.png)

上記の手動フローに加えて、ツールは**インポート時に自動ベイク**できます。ルールに一致したモデルが（再）インポートされた瞬間に、スムース法線がメッシュへ書き込まれます —— ツールを手動で実行する必要も、独立した Mesh として保存する必要もありません。

**非破壊的**：書き込みはインポート処理中、インポート対象のメッシュに対して行われ、インポート成果物とともに保存されます。ルールに一致しないよう変更するか、スイッチをオフにして再インポートすれば、元のメッシュに戻ります。

### 有効化と設定

ツールウィンドウ上部の **「インポート自動ベイク」タブ** を開きます：

| 設定 | 説明 |
|---|---|
| **インポート時の自動ベイクを有効化** | マスタースイッチ。既定はオフ。 |
| **判定ルール** | 独立して有効化できる 2 つの条件。詳細は次節を参照。 |
| **保存方式** | 頂点カラー / 接線チャンネル / `TEXCOORD0`–`7`。手動フローと同じ意味。シェーダー側も同じチャンネルを選ぶ必要があります。詳細は[保存方式](#保存方式)を参照。 |
| **保存空間** | オブジェクト空間 / 接線空間。既定は接線空間。シェーダー側も同じ空間を選ぶ必要があります。詳細は[保存空間](#保存空間)を参照。接線チャンネル保存を選んだ場合は適用外となり、自動的にグレーアウトします。 |
| **結合トレランス** | 下記「結合トレランス」の節と同じ。 |

設定は `ProjectSettings/OutlineSmoothNormals.asset` に永続化され、プロジェクトと一緒にバージョン管理されるため、チームで同じ設定を共有できます。

> 設定を変更しても、すでにインポート済みのモデルは自動で再ベイクされません —— それらは一度再インポート（右クリック `Reimport`）してください。

### 判定ルール

2 つの条件はそれぞれ独立して有効化でき、**両方を有効にした場合は積集合**（両方を満たしたものだけベイク）になります：

| 条件 | 説明 |
|---|---|
| **ファイル名の接尾辞で判定** | ファイル名（拡張子を除く）が指定した接尾辞で終わること。大文字小文字は区別しません。既定は有効で、接尾辞の既定は `_Outline`、例 `Hero_Outline.fbx`。 |
| **フォルダーパスで判定** | アセットが指定したフォルダー**およびそのサブフォルダー**の下にあること。オブジェクト欄へフォルダーをドラッグするだけです。 |

例：両方を有効にし、接尾辞を `_Outline`、フォルダーを `Assets/Characters` にすると、`Assets/Characters/**/Hero_Outline.fbx` のようなモデルだけがベイクされます。

- フォルダーは**パスの前方一致**をディレクトリ区切りまで見るため、`Assets/Characters2/` や `Assets/Old/Characters_backup/` のような同階層のディレクトリが誤って一致することは**ありません**。
- どちらの条件も**空なら不一致**として扱われます（接尾辞が空、またはフォルダー未指定）。**両方とも無効の場合も、どのモデルにも一致しません**。空の設定が「すべてに一致」と解釈されることは決してありません —— さもないと設定を書き終える前の瞬間に、プロジェクト全体のモデルが書き換えられてしまいます。
- モデルの**名前を変えて接尾辞を付ける**、**対象フォルダーへドラッグする**のどちらも Unity の再インポートを引き起こしませんが、ツールはこの種の移動を検知して再インポートを 1 回補います。

### 拡張フック（上級）

内蔵の「判定ルール＋3 つの保存方式」で対応できない自社パイプライン向けに、2 つの static デリゲートで引き取れます。未設定なら既定にフォールバックします。通常は `[InitializeOnLoadMethod]` で読み込み時に一度だけ代入します：

```csharp
using UnityEditor;
using OutlineSmoothNormalsGenerator;

static class MyOutlineAutoBake
{
    [InitializeOnLoadMethod]
    static void Register()
    {
        // カスタム判定ルール：ラベル / インポート設定などで判断し、内蔵の接尾辞とフォルダーの条件を置き換える
        OutlineNormalsImportProcessor.ShouldBakeRule = (assetPath, importer) =>
            assetPath.StartsWith("Assets/Characters/");

        // カスタム保存：メッシュとオブジェクト空間のスムース法線を受け取り、自前でエンコード / 書き込み
        OutlineNormalsImportProcessor.CustomStorageWriter = (mesh, smoothNormals) =>
        {
            // ……自社の書き込みロジック。シェーダー側は対応するフォーマットで読み取る……
        };
    }
}
```

### メッシュ健全性チェック

生成 / ベイクの前に、ツールはメッシュデータを走査し、処理できない、または結果に影響する問題（法線欠落、ゼロ / NaN 法線、退化三角形、同一位置への頂点重複過多、Read/Write 無効など）を報告します。手動フローでは「生成」ブロックの上部にカードとして表示され（エラー時は生成前に確認）、自動ベイク時は Console ログに書き出され、エラーのメッシュは自動的にスキップされます。

### TEXCOORD の命名について

チャンネルは 8 つ（`TEXCOORD0`–`TEXCOORD7`）あり、常に **`TEXCOORDn`** と呼び、`mesh.SetUVs(n)` のインデックスと**恒等に対応**します。

「UV1 / UV2」という呼び方を避けるのには理由があります：Unity 自身の `mesh.uv2` は実は `TEXCOORD1` であり、名前とインデックスが自然に 1 つずれていて、非常に間違えやすいのです。

> ⚠️ **`TEXCOORD0` はモデルのメインテクスチャ UV**（`mesh.uv`）です。書き込むとテクスチャマッピングが壊れ、その sharedMesh を参照するすべてのオブジェクトに影響します。既定は `TEXCOORD1` です。そのチャンネルが本当に空いている（プロシージャルメッシュなど）場合にのみ `TEXCOORD0` を選んでください。ツールは確認を求めます。

## 結合トレランス

「同じ位置」の頂点は結合して平均されます。しかし継ぎ目の頂点は DCC 書き出し、FBX の浮動小数点丸め、スケーリングを経て 1e-6 程度ずれるのが普通で、厳密な等値判定では結合されず、ツールは最も効いてほしい継ぎ目でこっそり失敗してしまいます。そこで**結合トレランス**（既定 `0.0001`）を用意しています。

> **既知の制限**：内部では位置をトレランスで整数グリッドに量子化します。ちょうどグリッド境界をまたぐ 2 点は依然として分離されます。完全に正しくするには近傍セル探索や Union-Find が必要です。丸めは標準的な手法で、代償として**トレランスはモデルの最小の実特徴サイズよりも十分小さくする必要があります** —— トレランスが大きすぎると、分けるべき頂点を誤って結合し、アウトラインが変形します。

## データ状態

右側の「データチャンネル状態の一覧」が各チャンネルの状態を表示します：

- `● スムース法線の可能性` — 強いヒューリスティックに一致
- `▲ 旧フォーマットの可能性` — TEXCOORD のみ：成分数が 3 で、`1.6.x` 以前でベイクされたデータの疑いあり。再ベイクが必要
- `○ データあり` — データはあるが、スムース法線かどうかは判定不能
- `✕ 空` — そのチャンネルにデータなし

> なぜ最高でも「**可能性**」までか：あるチャンネルが本当にスムース法線を保持しているかは、**データからは判定できません** —— エンコード後はただの数値の並びで、任意の頂点カラー / テクスチャ UV と区別がつきません。判定できると称するのは嘘になります。
>
> `1.7.0` 以降、TEXCOORD の事情は変わりました：本ツールは 2 成分を書き込み、テクスチャ UV も通常 2 成分なので、**新フォーマットのデータは「データあり」としか報告できません**。もともとスムース法線を見分けるのに使っていた信号（3 成分＋ほぼ単位長）は、逆に「これは旧フォーマットだ」というヒントになりました —— ただしこれも同じく強いヒントにすぎず、メッシュ結合は UV の次元を最大値に揃えますし、3 成分の方向を UV へ書き込む他のツールも一致します。頂点カラーは従来どおり「あり / なし」だけを報告します。

## データ安全性

| ボタン | 作用 |
|---|---|
| `保存` | **チェックしたすべての**メッシュの変更を各 `.asset` へ書き戻します。メッシュが書き込み不可のときは**阻止**して理由を説明し、成功を偽ることは決してありません。 |
| `⧉ 独立した Mesh として保存…` | **チェックしたすべての**メッシュを書き込み可能な `.asset` に複製します（1 つなら命名ダイアログ、複数ならフォルダー選択＋一括生成）。シーンオブジェクトには自動で再割り当て。書き込み不可のメッシュの唯一の出口です。 |
| `↺ 今回の変更を元に戻す` | 今回の生成 / クリア前の状態へ戻します。 |

> **本ツールは Unity の Undo に依存しません。** `Undo.RecordObject` はメッシュの頂点データを確実には追跡できず、変更不可のインポート済みサブアセットには全く効きません。「今回の変更を元に戻す」はツール独自のセッションスナップショットで、これを正としてください —— ウィンドウを閉じる、または対象を切り替えるとスナップショットは無効になります。

クリア操作は各保存方式のパネル内にあります（頂点カラーはペア単位でクリア、接線は「接線を再計算」で本物の接線を復元、TEXCOORD はチャンネル単位でクリア）。

## ゲーム内でアウトラインを使う

### 方法 1：Sample のシェーダーをそのまま使う

1. モデル用に新しいマテリアルを作成し、シェーダーを `OutlineSmoothNormalsGenerator/Outline URP`（または `... /Outline Built-in`）に設定します。
2. **Smooth Normal Source** で、**生成時と同じ**保存チャンネルを選びます（頂点カラー / 接線チャンネル / `TEXCOORD0`–`TEXCOORD7`）。頂点カラーモードでは **Vertex Color Channel** もベイク時と同じペアに設定してください。
3. **Smooth Normal Space** を生成時と同じ[保存空間](#保存空間)に設定します（既定は `Tangent Space`）。⚠ ここを間違えても**エラーは出ず**、アウトライン全体が傾くだけです —— アウトラインの不具合を調べるときは、まずこの項目を確認してください。
4. アウトラインの色と幅を調整します。**幅モード**は **スクリーンスペース**（等幅・距離に依存しない）または **ワールドスペース**（ワールド単位でオフセット・距離とともに縮小）から選べます。

`VertexNormal` モードは元の頂点法線に沿って押し出します。つまり「本ツールを使わない場合」の見た目で、直接比較に使えます。

シェーダーは 2 パス構成です：`OUTLINE`（表面カリングした押し出しアウトライン）＋ `FORWARD`（基本 NPR：2 段トゥーン陰影＋リム、マテリアルパネルで調整可能）。マテリアルの **Base Color Mode** には、スムース法線データをそのまま色として表示する**デバッグ用の段階**（頂点カラー / 接線 / `UV0`–`UV7`、ライティングなし）もあり、生成結果を目視で確認できます。製品時は **Base Map** に戻してください。

### 方法 2：Pass テンプレートで自分のシェーダーへ組み込む（推奨）

実際のプロジェクトには通常、自前のメインマテリアルがあります。本パッケージには既製の `OUTLINE` Pass テンプレートが入っており、**組み込みは 2 ステップだけ、デコード処理を書き写す必要は一切ありません**。以降ライブラリを更新すれば自分のシェーダーも一緒に更新され、手作業で追従する必要はありません。

Demo の 2 つのアウトラインシェーダーもこの経路を通っています —— テンプレートに問題があれば Demo が真っ先に露呈します。

#### ステップ 1：アウトライン用の 6 つのプロパティを追加

ShaderLab はマクロに対応していないため、`Properties` のこの部分だけはコピーするしかありません：

```shaderlab
[Header(Outline)]
_OutlineColor   ("Outline Color", Color) = (0,0,0,1)
[PowerSlider(3.0)]
_OutlineWidth   ("Outline Width", Range(0, 0.1)) = 0.015
[Enum(Screen Space, 0, World Space, 1)]
_OutlineWidthMode ("Outline Width Mode", Float) = 0
_SmoothNormalSrc ("Smooth Normal Source", Float) = 0
[Enum(RG, 0, GB, 1, BA, 2)]
_VCChannel      ("Vertex Color Channel", Float) = 2
[Enum(Object Space, 0, Tangent Space, 1)]
_SmoothNormalSpace ("Smooth Normal Space", Float) = 1
```

`_SmoothNormalSrc` は 11 段あり `[KeywordEnum]` の上限を超えるため、`[Enum]` を付けていません。ドロップダウンが欲しい場合は、シェーダー末尾の `CustomEditor` を本パッケージのカスタムインスペクターに設定してください：

```shaderlab
CustomEditor "OutlineSmoothNormalsGenerator.OutlineShaderGUI"
```

#### ステップ 2：Pass を 1 つ追加

**URP** —— まるごとコピー：

```shaderlab
Pass
{
    Name "OUTLINE"
    Tags { "LightMode" = "SRPDefaultUnlit" }

    Cull Front          // 背面だけを描き、はみ出した縁がアウトラインになる
    ZWrite On
    ZTest LEqual

    HLSLPROGRAM
    #pragma vertex   OSN_OutlineVert
    #pragma fragment OSN_OutlineFrag

    #include "Packages/com.unity.render-pipelines.universal/ShaderLibrary/Core.hlsl"
    #include "Packages/com.alefeng.outlinesmoothnormalsgenerator/Shader/OutlineSmoothNormals.hlsl"

    CBUFFER_START(UnityPerMaterial)
        // ↓↓ 自分のマテリアルプロパティ。他の Pass の CBUFFER と完全に一致させること
        float4 _BaseColor;
        float4 _BaseMap_ST;
        // ↑↑
        OSN_OUTLINE_MATERIAL_FIELDS
    CBUFFER_END

    #include "Packages/com.alefeng.outlinesmoothnormalsgenerator/Shader/OutlinePassURP.hlsl"
    ENDHLSL
}
```

**Built-in** —— まるごとコピー：

```shaderlab
Pass
{
    Name "OUTLINE"
    Tags { "LightMode" = "Always" }

    Cull Front
    ZWrite On
    ZTest LEqual

    CGPROGRAM
    #pragma vertex   OSN_OutlineVert
    #pragma fragment OSN_OutlineFrag

    #include "UnityCG.cginc"
    #include "Packages/com.alefeng.outlinesmoothnormalsgenerator/Shader/OutlineSmoothNormals.hlsl"

    // Built-in には SRP Batcher がないため、通常の uniform として宣言すればよく、CBUFFER は不要。
    OSN_OUTLINE_MATERIAL_FIELDS

    #include "Packages/com.alefeng.outlinesmoothnormalsgenerator/Shader/OutlinePassBuiltIn.hlsl"
    ENDCG
}
```

#### 必ず押さえる 4 点

- **include の順序は変えられません。** `OutlineSmoothNormals.hlsl` はプロパティ宣言の**前**（宣言がその中のマクロを使うため）、Pass テンプレートは**後**（テンプレート内の頂点シェーダーがこれらの uniform を使うため）です。順序を間違えるとそのままコンパイルエラーになります。

- **SRP Batcher（URP のみ）：`UnityPerMaterial` は各 Pass で一字一句同じにすること。** 1 項目でも欠けたり順序が違ったりすると、batcher は**黙って無効化**されます —— エラーは出ず、性能だけが落ちるので最も調べにくい類です。そのためアウトラインのプロパティは `OSN_OUTLINE_MATERIAL_FIELDS` で**唯一の**その CBUFFER に組み込み、**自分のすべての Pass にもこのマクロを**同じ位置で入れてください。

- **アウトライン Pass は基本描画 Pass より前に置くこと。** `Cull Front + ZWrite On` で先に背面の深度を書いておくことで、表面が内側を正しく覆えます。

- **`LightMode`**：URP は `SRPDefaultUnlit` を使い、アウトライン Pass は自動的に描画されるので Renderer Feature は不要です。Built-in は `Always` を使い、その Pass がライティングと無関係でオブジェクトごとに 1 回だけ描画されることを示します（`ForwardBase` にするとライトごとの描画に参加して重複描画されます）。

アウトラインの色の求め方だけを変えたい（テクスチャに応じてアウトラインの色を変えるなど）？テンプレートは書き換えず、自分で frag を書いて `#pragma fragment` をそちらへ向ければ済みます。`OSN_OutlineVert` はそのまま使えます。

## シェーダーでスムース法線を読む

上記の Pass テンプレートで通常は十分です。本節は**頂点シェーダーを完全に自分で握る必要がある**人向けです —— アウトラインに頂点アニメーションを重ねたい、あるいは頂点帯域にシビアでテンプレートの 8 つの TEXCOORD を宣言したくない、といった場合です。

**いずれにせよ共有ライブラリを `#include` することを推奨**します。デコードを自前で書き写すのはやめてください —— それこそがこのプラグイン初期の「プレビューと実際が一致しない」一連の不具合の元でした。

### 汎用の書き方（マテリアル側で保存方式をランタイム切り替えできる）

```hlsl
#include "Packages/com.alefeng.outlinesmoothnormalsgenerator/Shader/OutlineSmoothNormals.hlsl"

// ① スムース法線を取得：デコード＋空間復元を一度に行う
float3 smoothNormalOS = OSN_GetSmoothNormalOS(
    _SmoothNormalSrc, _SmoothNormalSpace, v.color, v.tangent,
    v.uv0.xyz, v.uv1.xyz, v.uv2.xyz, v.uv3.xyz,
    v.uv4.xyz, v.uv5.xyz, v.uv6.xyz, v.uv7.xyz,
    v.normal, _VCChannel);

// ② 押し出し（URP 記法。Built-in では 2 つの Transform を
//    UnityObjectToWorldNormal / UnityObjectToClipPos に置き換える）
float3 normalWS = TransformObjectToWorldNormal(smoothNormalOS);
float4 clipPos  = TransformObjectToHClip(v.positionOS.xyz);
o.positionCS    = OSN_ApplyOutlineOffset(clipPos, normalWS, _OutlineWidth, _OutlineWidthMode);
```

`OSN_GetSmoothNormalOS` の中身は「デコード → 保存空間に応じた復元」の 2 段です。この 2 段は**必ず対で現れる必要があり**、後段を落としてもエラーは一切出ず、アウトライン全体が傾くだけです —— そのため 1 つの関数にまとめました。どうしても分けて呼びたい場合は、それぞれ `OSN_SelectSmoothNormalOS` と `OSN_ResolveSmoothNormalSpace` です。

`OSN_ApplyOutlineOffset` は、間違えやすい 3 つの処理を内部で行います：逆転置行列で法線を変換（さもないと非一様スケール下でアウトラインが傾く）、オフセット方向を**クリップ空間**で取る（さもないと FOV / アスペクト比の影響を受ける）、ゼロ長方向へのガード（さもないと法線がカメラ正面を向いたとき `normalize` が NaN を生み、GPU が三角形ごと破棄する）。最後の引数は幅モードです：`0` はスクリーンスペース（等幅）、`1` はワールドスペース（距離とともに縮小）。

### 最小の書き方（保存方式をシェーダーに固定する）

製品プロジェクトでは、プロジェクト全体で保存方式を 1 つに統一することがほとんどです。その場合マテリアル側のランタイム切り替えを残す必要はなく、8 つの TEXCOORD を宣言する必要もありません —— 対応するデコーダーを直接呼ぶだけで、分岐はゼロです：

```hlsl
// 例：プロジェクト全体で「頂点カラー BA ＋ 接線空間」に統一
// 頂点入力に必要なのは POSITION / NORMAL / TANGENT / COLOR だけで、UV は 1 つも宣言不要
float3 smoothNormalOS = OSN_OctDecode(v.color.ba);                       // 頂点カラー BA をデコード
smoothNormalOS = OSN_TangentToObject(smoothNormalOS, v.normal, v.tangent); // 接線空間 → オブジェクト空間
```

オブジェクト空間保存なら 2 行目は不要です。TEXCOORD 保存なら 1 行目を `OSN_OctDecode(v.uv1.xy)` に置き換えます（このチャンネルには 2 成分の八面体が格納されており、頂点カラーと同じエンコードですが精度ははるかに高いです）。接線チャンネル保存なら `normalize(v.tangent.xyz)` に置き換えます（そのモードは常にオブジェクト空間なので、2 行目も不要です）。

> ⚠️ **`1.6.x` 以前からアップグレードするプロジェクトは注意**：この行は以前 `normalize(v.uv1.xyz)` でした。本ライブラリのデコーダーを呼んでいないため、パッケージを更新しただけでは**すぐにおかしくなることはありません** —— しかし**一度ベイクし直すと壊れます**。`OSN_OctDecode(v.uv1.xy)` への変更とベイクし直しは、必ずセットで行ってください。詳細は[1.6.x 以前からのアップグレード](#16x-以前からのアップグレード)を参照。

このときマテリアルパネルの `Smooth Normal Source` / `Smooth Normal Space` は有名無実になるので、この 2 つのプロパティは宣言しなくてもかまいません —— ただし**どの組み合わせを固定したのかを必ずシェーダー内のコメントに明記してください**。さもないと後日保存方式を変えるときに手掛かりがなくなります。

### まったく include したくない場合

接線チャンネルモードだけが、**オブジェクト空間保存のとき**にそのまま正規化して方向を取れます：

```hlsl
float3 smoothNormalOS = normalize(v.tangent.xyz);
```

頂点カラーと TEXCOORD はどちらも八面体エンコードなので、デコードが必要です —— 両者は同じ関数を共有しており、違うのは値を取る位置と精度だけです（頂点カラーは 8-bit × 2、TEXCOORD は float × 2）：

```hlsl
float3 OctDecode(float2 f)
{
    f = f * 2.0 - 1.0;
    float3 n = float3(f.x, f.y, 1.0 - abs(f.x) - abs(f.y));
    float  t = saturate(-n.z);
    n.xy += (n.xy >= 0.0) ? -t : t;
    return normalize(n);
}

float3 smoothNormalOS = OctDecode(v.color.ba);  // 頂点カラー BA チャンネルペア
float3 smoothNormalOS = OctDecode(v.uv1.xy);    // または TEXCOORD1
```

⚠ ベイク時に既定の**接線空間**を使った場合は、さらに自分で TBN を再構築して戻す必要があります —— それこそが `OSN_TangentToObject` の仕事であり、自前で書き写すと Gram-Schmidt 直交化や手性 `tangent.w` で間違えやすいところです。

**この道はおすすめしません**。しかも前例がすでに 2 回あります：書き写したコードはライブラリの更新に追従しないため、`1.5.0` で保存空間が追加されたときは手写しのシェーダーすべてに手動で 1 段足す必要があり、抜けてもエラーは出ず、アウトラインがこっそり傾くだけでした。`1.7.0` では TEXCOORD のエンコードフォーマットを変更したため、`normalize(v.uv1.xyz)` を手書きしていたプロジェクトも同様に、上記の書き方へ手動で変更する必要があります。

## 注意事項

- スムース法線の計算は**頂点位置の結合**に基づき、トレランスの既定は `0.0001` です（上記「結合トレランス」参照）。
- `sharedMesh` を変更すると、そのメッシュを使う**すべての**オブジェクトに影響します。単一のオブジェクトだけに適用したい場合は、先に「独立した Mesh として保存」で複製してください。
- **接線チャンネルモードはメッシュの元の接線を上書きする**ため、ノーマルマップをサンプリングするシェーダーは誤った TBN を得ます。
- `Editor/Shader/OutlinePreview.shader` はエディタープレビュー専用です —— 製品用途には使わないでください。欠落している場合（通常はパッケージのインストールが不完全）、プレビューは単色に退化し、アウトラインのオフセットがなくなります。
- 格納されるのは常に**完全な三次元方向**で、半球圧縮は行いません。オブジェクト空間と接線空間のどちらで書くかは[保存空間](#保存空間)で決まります。
- **`1.7.0` から TEXCOORD チャンネルは 2 成分の八面体エンコードで格納する**ため、テクスチャ UV とは次元でも値域でも区別がつかず、チャンネル状態は「データあり」としか報告できません。逆に「成分数が 3」が旧データを見分けるヒントになりましたが、これも同じく強いヒントであって判定ではありません（[データ状態](#データ状態)を参照）。
- ⚠ **`1.6.x` 以前からのアップグレード**：UV 保存のデータフォーマットが変更されたため、ベイクし直しが必須です —— 完全な移行手順は[1.6.x 以前からのアップグレード](#16x-以前からのアップグレード)を参照してください。頂点カラーまたは接線チャンネルだけを使っているプロジェクトは影響を受けません。
- ⚠ **`1.4.x` からのアップグレード**：`1.5.0` から保存空間の既定は接線空間になり、マテリアルの **Smooth Normal Space** も既定が `Tangent Space` になりました。一方、古いデータはすべてオブジェクト空間でベイクされています —— **一度ベイクし直す**か、マテリアルのこの項目を `Object Space` に戻してください。[インポート時の自動ベイク](#インポート時の自動ベイク)を使っているモデルは自動で再ベイクされるため、対応は不要です。
- `1.0.0` より前の内部バージョンでベイクしたメッシュは**再ベイク**が必要です。
